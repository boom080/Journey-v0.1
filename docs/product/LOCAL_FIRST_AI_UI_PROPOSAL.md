# Journey 本地优先与 AI 原生首页提案

**Status: Partially Implemented（方案 C 视觉子项已实现；本地数据与小红书仍 Proposed）**
**Date: 2026-08-04**
**Scope: 阶段 12 产品定义，以及用户确认后的首页视觉子项；不含数据库、API、Agent 或 Web Research**

## 1. 本轮结论

Journey 下一轮不应继续在当前大卡片上做局部美化，而应同时解决两个产品问题：

1. 把“没网就几乎不能用”改为“核心个人数据本地可读写，联网后同步”；
2. 把首页从复古记录面板改为 AI 原生的健康伙伴入口，同时保留 Journey 的薄荷绿、叶子角色和
   “首页 / Journey / 我的”三个一级入口。

方案 C 的视觉方向已由用户确认并落地；完整本地数据副本与小红书路径仍只定义目标、边界和
可量化验收标准，未获确认前不进入实现。

## 2. 当前截图审计

### 已有优点

- 薄荷绿与叶子角色已经形成可识别的 Journey 品牌资产；
- 首页信息集中，用户能理解这里是统一记录入口；
- 离线状态有明确反馈，没有假装 Agent 仍然可用；
- 卡片圆角和大字号适合手机点击与求职现场演示。

### 需要解决的问题

- 首屏 Hero 过高，真正的输入框被推到折叠线以下，违背“打开就能输入”的产品原则；
- “随手记一下”在窄屏被拆成三行，视觉重心破碎；
- 吉祥物仍像一张带方形底色的贴图，没有融入界面环境；
- 页面几乎所有区域都是等权重大圆角矩形，缺少层次、留白和轻盈感；
- 黄色离线警告占据核心位置，用户首先感受到的是限制，而不是还能完成的任务；
- 缺少清晰的 AI 状态、下一步建议和今日进度，整体更像传统表单首页而不是健康 Agent。

## 3. 离线能力矩阵

下表是建议目标，不代表当前代码已经实现。当前代码事实见
[`CURRENT_PROJECT_AUDIT.md`](../CURRENT_PROJECT_AUDIT.md)。

| 能力 | 在线 | 离线建议 | 恢复联网后 | 产品边界 |
|---|---|---|---|---|
| 首次注册、登录、找回密码 | 完整 | 不可用 | 重新发起 | 密码不落本地业务缓存 |
| 已登录用户进入 App | 完整 | 使用安全会话与本地账户数据进入 | 静默校验会话 | 会话失效时要求重新登录 |
| 画像、目标读取 | 服务端最新 | 本地完整可读 | 以版本号增量同步 | 按账户隔离，退出时清除 |
| 画像、目标编辑 | 直接写 API | 本地保存为待同步变更 | 自动同步；冲突需提示 | 不静默覆盖服务器新版本 |
| 饮食、运动、体重新增 | 直接写 API | 本地新增并进入 Outbox | 幂等上传、回填服务端 ID | 显示“已保存到本机” |
| 记录编辑、删除 | 直接写 API | 可排队，但显示待同步状态 | 检查版本冲突后执行 | 冲突由用户选择，不自动丢数据 |
| Journey 历史 | 服务端 + 本地 | 浏览已同步记录 | 增量拉取并合并 | 无缓存时显示友好空状态 |
| 文字 Agent | 真实/Mock Provider | 不可用 | 用户主动重新提交 | 不把本地规则冒充为 Agent |
| 本地快速归类 | 可用 | 饮食/运动/体重的确定性解析 | 转为标准业务记录同步 | 只处理明确、低风险输入 |
| 本地健康常识 | 受控 RAG | 随安装包提供少量只读内容 | 可更新知识包 | 仅生活方式常识，不作医疗建议 |
| 个性化建议、周总结 | Agent 工作流 | 不生成新结果；可读旧结果 | 用户主动刷新 | 不使用过期数据伪装实时建议 |
| 食物图片候选 | Development 实验性 | 不可用 | 用户重新选择图片并提交 | 图片质量仍为 No-Go |

### 推荐的本地事实源

- PostgreSQL 仍是跨设备同步事实源；移动端数据库是当前设备的可用副本，不是第二套独立业务；
- 首次成功登录后同步该账户的画像、目标和全部规范化健康记录。当前个人使用规模较小，优先
  保证完整可用；后续再按数据量增加可配置保留期；
- 每条本地变更保存 `local_id`、`server_id`、版本、更新时间、同步状态和幂等键；
- 同一字段双端都修改时不采用“最后写入者静默获胜”，必须显示冲突卡片供用户确认；
- 退出账号时清除该账户的本地健康数据、查询缓存与待同步队列；服务端数据不受影响；
- 本地数据库与队列需要设备级加密密钥；模型 Key、账号密码和完整 Authorization 不进入缓存。

## 4. 首页信息架构

首页首屏按以下优先级排列：

1. 轻量问候 + AI/离线状态；
2. 统一文字输入框，首屏直接可见；
3. 低负担快捷提示，例如“午饭吃了…”“跑了 30 分钟”“今天还差多少蛋白质”；
4. 今日能量、运动、体重趋势等最重要的 2—3 个数据；
5. Agent 正在执行的计划、待确认候选或一个清晰的下一步；
6. 底部固定三个一级入口：首页、Journey、我的。

离线不再出现占据整屏的警告卡。顶部状态改为“离线可记录”，输入框下只提示“记录已保存在
本机，联网后自动同步”；在线 Agent 能力采用状态徽标和渐进式进度反馈。

## 5. 视觉方向迭代

### 已否决方向

用户于 2026-08-04 明确否决第一轮“温和 AI 健康伙伴”和“轻量数据智能”两套稿：整体过暗，
偏灰绿，失去旧版暖白与明亮薄荷绿的亲和感；新画的简化叶子角色也不符合原版角色质量。两套稿
只保留为失败迭代记录，不再作为实现候选，也不采用“A 外壳 + B 数据密度”的组合建议。

### 方案 C：暖白薄荷 Journey（视觉子项已确认并实现）

- **固定浅色品牌体验**：页面以暖白 `#fbfffd`、浅薄荷 `#f2fcf7` 为大面积背景；主视觉使用
  旧版 `#74c7a2`、`#4fb387`、`#2f8f68` 附近的明亮薄荷梯度，不跟随系统深色模式变暗；
- **复用原版角色，不再手绘替代品**：首页只使用现有
  `assets/brand/journey-leaf-home.png`，用有机圆形裁切融入 Hero，消除方形贴图感；饮食和运动
  状态后续分别使用原版 food/activity 角色；
- **保留旧版温暖 Hero**：问候、日期和一句轻量鼓励保留，但 Hero 高度压缩，统一输入卡与其
  下沿轻微叠合，保证首屏可直接输入；
- **减少卡片数量**：主页面只保留 Hero、一个白色输入面和一个轻薄 Agent 状态条；今日三个
  指标采用开放式分栏，不再分别套大圆角卡；
- **AI 感来自行为而非深色科技风**：状态文案清楚展示“识别 → 工具 → 确认 → 更新”，不使用
  黑色、霓虹、玻璃拟态或大量仪表盘；
- **离线仍保持明亮**：仅把顶部状态改为“离线可记录”，输入辅助文案提示本机保存；不改变
  页面底色，不展示大面积黄色警告。

当前对话稿 `journey-warm-mint-home.html` 是确认来源；实际 App 已在
`apps/mobile/src/components/home-overview.tsx` 实现同一方向。实现保持既有 API、Agent 和
数据库契约不变；这不代表完整 local-first 能力已经完成。

### 视觉实现验收（2026-08-04）

- 390 × 844 与 320 × 844 浏览器手机视口均人工核对：主标题完整、输入首屏可见、三个指标
  数值不截断，没有横向滚动；
- 原版 `journey-leaf-home.png` 进入 Web、iOS 和 Android bundle；固定浅色主题避免系统深色
  模式把品牌页变成暗灰；
- 离线仍只显示当前真实能力：手动记录可保存并待同步，Agent 与图片不可用；没有把未完成的
  完整本地画像/历史能力写成已实现；
- TypeScript、Expo lint、33 条 Jest 组件/契约测试、5 条本地逻辑测试、2 条 Web E2E 及三端
  Expo export 均通过。

## 6. AI 状态与文案

| 状态 | 主文案 | 次文案/动作 |
|---|---|---|
| Online idle | 想记录什么？ | 直接说一句，Journey 会判断该怎么处理 |
| Planning | 正在整理这件事 | 展示 1—3 个可读步骤，不展示思维链 |
| Tool running | 正在读取你的近期记录 | 显示工具名称的用户语言，不暴露内部参数 |
| Waiting | 等你确认后继续 | 突出候选与校正入口，不自动写入 |
| Completed | 已记录，并更新了今天 | 给出结果、依据和下一步 |
| Offline | 离线可记录 | 已保存在本机，联网后自动同步 |
| Sync conflict | 有一项需要你选择 | 并排呈现本机版本和云端版本 |
| Failure | 这次没完成 | 说明失败位置、已保留的内容和可重试动作 |

## 7. 小红书与浏览器能力边界

### 当前事实

Journey 的 Agent 当前没有浏览器或通用网页搜索工具。现有 `knowledge.retrieve` 是项目控制的
RAG 检索，模型调用是 Provider API；两者都不等于可以打开浏览器、登录网站或浏览小红书。

截至 2026-08-04，可公开确认的小红书开放能力主要面向商品、库存、订单等商家场景，以及
小红书小程序、笔记发布和经营入口。当前公开文档没有证明存在一个可供 Journey 任意搜索消费
者笔记、读取推荐流或批量摄取生活内容的公共 API：

- [小红书 Ark 开放平台简介](https://school.xiaohongshu.com/en/open/quick-start/introduction.html)
  明确聚焦商品信息、库存、价格和包裹管理；
- [小红书小程序开放平台](https://redopen.xiaohongshu.com/)介绍小程序入驻、端内入口和笔记
  发布能力，不等同于公共笔记搜索接口；
- [小红书开放平台开发者协议](https://xiaohongshu.apifox.cn/doc-2811022)要求合法渠道、明确
  同意和最小必要，并禁止获取用户账号密码/认证凭据或代理用户自动登录；内容和平台运营数据
  也受知识产权及使用许可约束。

### 推荐路径

1. **近期首选：用户主动分享链接。** 用户在小红书点“分享/复制链接”，Journey 接收 URL，
   只提取公开页面允许读取的标题、短摘要和来源链接；用户确认后再保存为生活灵感。不得批量
   复制正文、图片或绕过登录/反爬限制。
2. **通用受控浏览工具。** 后续单独建立只访问公开网页的 `Web Research Tool`：域名白名单、
   SSRF 防护、超时/大小限制、无 Cookie、无账号密码、引用来源与日期、完整审计。它可以扩展
   年轻生活方式信息源，但不能把社交帖子当作医学或营养事实。
3. **官方授权优先。** 如果未来获得小红书正式应用、OAuth 和明确包含所需内容的 Scope，再
   通过官方 API 接入；在此之前不声称“已绑定小红书”。
4. **可信度分层。** 小红书等生活内容只用于灵感、趋势和偏好候选；营养数值、健康安全和
   解释依据必须回到受控知识库或权威公开来源，并在回答中区分“生活灵感”和“健康证据”。

### 明确禁止

- 不让用户把小红书账号、密码、Cookie 或验证码交给 Journey；
- 不由 Agent 操作用户已登录浏览器进行后台抓取、关注、点赞、私信或自动发布；
- 不爬取推荐流、批量保存帖子/图片、规避访问控制或以“仅个人使用”为由绕过平台规则；
- 不把未经核验的博主经验直接写成个性化健康结论。

## 8. 量化验收标准

### 首屏和视觉

- 390 × 844 pt 参考屏上，统一输入框顶部必须位于首屏高度的 38% 以内；无需滚动即可输入；
- 320 pt 宽度不出现标题单字孤行、横向滚动或按钮重叠；动态字号 120% 仍可完成主流程；
- 首页首屏最多 1 个大面积容器、2 个次级容器；不允许所有信息都使用等权重大卡片；
- 吉祥物使用透明背景或与背景自然融合，不出现可见方形贴图底；
- 正文与背景对比度达到 WCAG AA；点击目标不小于 44 × 44 pt；
- 5 名目标用户的盲测中，至少 4 人在 5 秒内指出“从哪里开始记录”。

### 离线与同步

- 完成一次登录和全量同步后，飞行模式下画像/目标/历史可读率为 100%；
- 离线新增饮食、运动、体重成功率为 100%，状态必须明确标注“本机已保存/待同步”；
- 恢复网络后 30 秒内自动同步成功率 ≥99%（1000 条故障注入样本），重复业务写入为 0；
- 退出账号后本地该账户健康数据、缓存和 Outbox 残留为 0；不同账户数据泄漏为 0；
- 冲突测试中静默覆盖率为 0，用户选择后最终一致率为 100%；
- 离线状态不得发起模型、图片或 Web Research 外部请求，外部调用数为 0。

### Agent 与生活内容

- 在线/离线状态识别准确率 100%，离线不得把确定性分类文案标记为 AI/Agent 结果；
- 任何 Web Research 结果必须有 URL、来源名称和抓取日期，引用字段完整率 100%；
- 小红书导入必须由用户逐次主动分享触发，后台自动抓取或使用登录凭据次数为 0；
- 社交生活灵感与健康证据必须在 UI 和 Schema 中分层，未经权威来源支持的医疗/营养断言
  进入建议的比例为 0；
- 域名白名单、SSRF、超时、最大响应体、恶意页面和 Prompt Injection 测试通过率 100%。
