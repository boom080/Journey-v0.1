# Journey 简历描述与面试问答依据

> 当前口径：2026-08-04 本机交付与真实模型验收基线。所有数字均来自仓库内报告或实际命令；不要把
> Simulator、debug-certificate APK、Mock 评测或本机 staging 表述成已上架、生产部署或真实
> 图片模型质量通过。

## 一句话介绍

Journey 是一个从旧微信小程序渐进迁移而来的 Agent 增强健康管理应用：Expo/React Native
提供 iOS、Android、Web 单代码库，FastAPI/PostgreSQL 统一身份和健康记录，首页 Agent 把
自然语言解析成结构化候选，只有用户确认后才幂等写入。

## 简历项目描述

### 通用版

**Journey｜Agent 增强跨平台健康管理应用**

- 基于 Expo/React Native、FastAPI、PostgreSQL 构建 iOS、Android、Web 共享业务与后端的
  健康记录应用，完成邮箱/用户名身份、画像目标、饮食、运动、体重、首页聚合和 Journey。
- 设计“意图路由—计划—策略校验—工具执行—Observation—验证—有限重规划—人工确认—
  幂等写入/恢复”的单 Agent 闭环；组合任务先暂停，确认后基于最新业务事实继续执行，并使用
  LangChain/LangGraph 与模型适配层支持供应商切换、受控 RAG 和结构化线程记忆。
- 建立 85 条后端/API/数据库/评测测试（后端覆盖率 90.49%）、Requests + Pytest + Allure
  网络黑盒、31 条移动组件测试、5 条逻辑测试、2 条核心 Web E2E，以及 362 条版本化样本和
  26 项量化门禁；Allure、JUnit、Coverage 与 Agent JSON 报告并存，CI 使用 Mock/空真实 Key。
- 建立 CI Mock 与真实发布门禁分层：DeepSeek `deepseek-v4-flash` 首轮发现一条画像查询误路由，
  Router Prompt 升级后 28/28 达到路由/饮食/运动解析 100%、0 fallback、p95 1768 ms；
  Qwen 图片链路虽可运行，
  但独立质量门禁失败，因此保持实验性和正式环境关闭。
- 提供 Docker Compose 本机 staging、Alembic upgrade/downgrade 回环、iOS Simulator
  Release 与 Android ARM64 Release APK 构建安装路径，并保留 Web production export。

- 将旧产品收敛为“首页、Journey、我的”三个一级入口：首页统一输入自动分流饮食、运动、

- 用预注册指标验证食物图片方向；真实结果未达门槛后停止上线，保留研究证据，体现从需求、

## 60 秒面试开场

“我做的 Journey 不是简单套一个聊天接口，而是把旧微信健身小程序升级成可交付的跨平台
应用。用户在首页输入一句话，Router 和 Planner 生成结构化计划，Policy Guard 校验工具白名单
和人工确认，Executor 把结果转为 Observation，再由 Verifier 决定完成、等待、有限重规划或
停止；组合任务会在候选处暂停，只有用户确认写入 PostgreSQL 后才恢复并读取最新事实。线程
只保存服务端结构化摘要，所以切换模型不会丢失业务记忆。工程上我做了
85 条后端/评测测试、Requests 网络黑盒、31 条移动组件测试、5 条逻辑测试、2 条核心 E2E，
以及 362 条版本化评测和 26 项门禁；iOS 和 Android Release 都在模拟器真实安装运行。真实
DeepSeek 规划首轮因过度调用工具失败，Prompt 修正后通过；v3 的 checkpoint 与恢复门禁也
完成 10 次真实调用并全部通过；Qwen 图片 API 能运行但独立质量门禁不
达标，所以图片保持 No-Go。这两个失败—决策案例体现了项目的 Agent 工程和产品判断。”

## 可重点讲的三个 STAR 案例

### 1. 把不可控 Agent 变成可测试工作流

- S：普通 LLM 接口可能选错工具、参数不稳定，还会把候选直接当成事实。
- T：支持自然语言记录，同时保证健康记录可追踪、可回归。
- A：拆分 Router、Planner、Policy Guard、类型化工具、Observation、Verifier、Replanner、
  确认和恢复；版本化 Prompt/Schema/知识库；限制 6 步/2 次重规划并建立量化门禁。
- R：362 条 Mock 样本、26 项门禁全部通过，真实 Planner 首轮失败后按量化反馈修正；v3
  checkpoint/恢复真实门禁 10 次调用全部通过，模型失败仍可降级或手动记录，未确认写入为 0。

### 2. 用真实失败数据做产品 No-Go

- S：食物照片识别很有展示效果，但单张图片估重存在尺度和密度歧义。
- T：判断该能力是否值得进入正式产品。
- A：先冻结隐私边界和指标，再建设授权数据集、密封 holdout、尺度配对和一次性真实评测。
- R：识别 Top-3 与估重误差未达预注册门槛，因此正式环境保持关闭；结论、失败样本边界和
  重启条件写入 ADR。项目没有为了“功能多”牺牲可信度。

### 3. 隔离 E2E 发现配置缺陷

- S：单元测试全部通过，但全新隔离环境无法创建测试账号。
- T：证明新环境可以真正启动并完成核心演示。
- A：用独立 Compose 项目、临时数据库、空模型 Key 和 Mock 跑 Playwright；定位到环境模板
  密码不满足后端复杂度规则，修正模板并把规则加入配置校验脚本。
- R：两条核心 E2E 全部通过，后续无效模板会在构建前直接失败。

## 高频问答

### 为什么不做多 Agent 对话？

业务核心是可验证的记录和建议工作流。单 Agent + 类型化工具 + 有限状态图已经具备规划、
策略校验、执行、验证和受限恢复，更容易测试、追踪和控成本；没有真实业务必要时，多 Agent
只会增加上下文漂移和排障难度。

### 用户记忆放在哪里？

画像和历史记录存 PostgreSQL；Agent Thread 只保留最近 8 条不含原文的结构化摘要，由
Context Builder 按最小必要原则在每次请求中提供；公共知识进入受控 RAG。不能依赖某一模型
供应商的会话记忆，因为模型可切换，服务端数据才是事实源。

### 为什么必须用户确认后写入？

模型擅长解析候选，不应替代用户决定健康记录。候选与写入 API 分离能降低误记，支持审计，
也让工具参数和“未确认写入为 0”成为可量化测试对象。

### Mock 能证明什么，不能证明什么？

能证明路由、Schema、工具、状态机、RAG、trace、降级、客户端联动和成本记录；不能证明真实
模型的语义质量。因此项目另设真实发布门禁：当前 DeepSeek 文字门禁已通过，Qwen 图片功能
冒烟通过但质量门禁失败。供应商、模型 alias、地区、价格或政策变化后必须重新验收。

### 为什么选择模块化单体？

当前规模不需要微服务。模块化单体保留领域边界和测试隔离，同时减少部署、分布式事务和
可观测性成本；只有出现独立扩缩容或团队边界的实证需求才拆服务。

### 如何防止 Prompt 改坏？

Prompt、Schema、知识库和数据集都有版本；CI 对意图、工具、参数、引用、拒答、P95、Token
等阈值做回归。未达门禁不能合入，真实评测使用密封集且禁止根据失败样本重跑调参。

### 为什么主演示用 iOS Simulator？

它贴近目标发布端且电脑端鼠标操作稳定；Android Emulator 验证跨平台，Web 用于应急。三端
共用代码和契约，不维护两套业务前端。

### 隐私怎么做？

客户端模型 Key 为零；原生 Token 存 SecureStore，离线队列 AES-GCM 加密且 24 小时过期；
Agent trace 不落原始输入；图片原文不进入常规日志。正式供应商隐私政策和发布披露仍是门禁。

### 当前还有哪些不足？

- 没有付费 Apple Developer Program，因此只证明 Simulator，不声称 TestFlight/App Store。
- Android APK 使用 debug certificate，只用于本机安装；没有 Play upload key 或 AAB。
- 没有公网生产环境；当前是本机 staging，未来自租服务器需补 HTTPS、备份演练和监控。
- 普通 CI 使用 Mock；联网主演示可使用已通过门禁的 DeepSeek 文字模型。Mock 指标仍不能
  代替真实供应商质量，图片也不能因单张冒烟成功而宣称整体通过。
- 当前 npm 审计有 Expo/Jest/ESLint 构建与测试工具的上游传递依赖告警，自动修复会破坏当前
  Expo/Jest 版本，已记录为升级前风险而未执行 `--force`。
- 食物图片能力真实质量门禁失败，正式环境关闭；这应作为量化决策案例，而不是上线功能。
