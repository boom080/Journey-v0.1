## 一、现有版本的漏洞修复说明

本板块中的“漏洞”同时包含发布风险、可信度缺陷和核心体验故障。P0 必须在任何 Preview 或公开
演示前修复，P1 必须在 v0.2 功能封板前修复，P2 作为发布候选门禁处理。

| 编号 | 优先级 | 现状与影响 | 修复要求 | 验收标准 |
|---|---|---|---|---|
| FIX-01 | P0 | `apps/mobile/src/config/environment.ts` 的图片开关在未配置时默认开启；登录页无条件展示本地测试账号入口。实验能力可能错误进入 Preview/Production | 建立 Development、Preview、Production 的统一能力清单；图片、测试账号、Mock、原始 Trace 均默认关闭，只允许 Development 显式开启 | Production 构建扫描中相关入口和测试凭据为 0；三种变体自动化测试通过 |
| FIX-02 | P0 | `backend/app/agent/workflows.py` 允许模型返回非空知识答案但不给 citation id；历史 Citation Correctness 为 0.9083 | 在最终响应前增加 Citation Verifier；事实性健康答案必须至少有一个有效引用，否则重试或返回 `insufficient_context` | 引用覆盖率 100%，Citation Correctness ≥ 0.95，无依据拒答准确率 100% |
| FIX-03 | P0 | 真实 Provider 的数据发送范围、首次同意、保留说明和删除证明没有形成端到端发布门禁 | 增加外部模型使用说明与明确同意；仅发送最小上下文；日志、Trace 和错误全部脱敏；提供保留与删除说明 | 未同意时真实 Provider 调用为 0；敏感字段扫描为 0；删除流程有契约和 E2E 证据 |
| FIX-04 | P1 | 首页把网络连接直接显示为“Agent 在线”，没有验证 API readiness、Provider、预算或熔断状态 | 在线状态改为服务能力探测，明确区分离线、API 不可用、Provider 不可用、预算受限和降级 | 模拟各类故障时状态文案与可用操作正确，不能出现假在线 |
| FIX-05 | P1 | 真实 Agent 历史端到端请求约 20.4–28.02 秒，客户端以长同步请求等待，弱网、切后台和超时后的恢复体验不完整 | Run 先持久化再异步执行；快速返回 `run_id`；支持事件进度、取消、重连、查询最终态和幂等恢复 | 提交后 1 秒内显示确定性状态；首个服务端进度事件 P95 ≤ 2 秒；重复请求不重复写入或计费 |
| FIX-06 | P1 | `backend/app/agent/memory.py` 只保存最近 8 条 Run 的运行摘要，无法作为用户可控的长期记忆 | 将线程摘要与长期记忆分离；长期记忆必须类型化，并带来源、时间、置信度、有效期和用户确认状态 | 未确认推断写入长期记忆次数为 0；用户可查看、纠正、关闭和彻底删除 |
| FIX-07 | P1 | RAG 只有 4 个短知识文档，Embedding 是 96 维 hash chargram；覆盖面和语义泛化有限 | 先建立带来源、许可、地区和版本的知识源注册表，按固定 Eval 扩充小型受控语料；只有证据表明检索成为瓶颈时才升级 Embedding 或向量库 | RAG 固定集达到 Recall、MRR、Groundedness、Citation 和 Abstention 门禁，所有结果可追溯到语料版本 |
| FIX-08 | P1 | OpenTelemetry 只有局部 `agent.model` span，缺少完整 Run 的 exporter、collector 和链路关联 | 打通 request → run → plan → tool → model → verifier，统一记录延迟、错误、回退、token、成本和引用数 | 每条 Agent Run 都有完整 trace id；失败可定位到步骤和版本；日志与 span 不含敏感明文 |
| FIX-09 | P1 | 普通用户首页直接展示 Orchestrator、工具名、Provider、模型、延迟和费用；主题配置为 `automatic`，但视觉主要按浅色实现 | 用户层只展示结果、改动、依据和下一步；内部信息移入受限调试视图；v0.2 首发锁定完整浅色主题，补齐窄屏、动态字体和无障碍 | 主流程不出现内部工具和费用；320/390 pt、Android、Web 截图回归及读屏主路径通过 |
| FIX-10 | P2 | 根包、移动端和后端版本仍为 `0.1.0`；真实复合 Agent 与 Web E2E 样本较少；公网、备份恢复、告警和正式签名没有完整证据 | 统一升级版本；重跑全量基线；扩展核心 E2E、故障注入、备份恢复和发布验证；严格区分本机可演示、可部署与已上线 | 所有版本号一致；发布证据包包含 commit、环境、测试、Eval、已知限制和回滚方式；无证据时不得标记已上线 |

上表保留立项时的问题基线。截至 2026-09-01，`FIX-01`、`FIX-02` 的工程修复已完成；`FIX-03`
已补齐文字授权、最小上下文、脱敏、客户端、数据删除/保留、部署审核门禁及加密备份/隔离恢复工具。
实际 Journey 本机库已迁移至 `0008_agent_privacy`，两次隔离恢复演练通过，整体完成度 90%
（细化后 10 项检查中 9 项完成）。本机 100 条过期 Agent Run 及关联临时数据已清理，已确认健康
记录的数量和内容摘要保持一致；当前工作树构建的新版 API 已健康启动。文字外部模型、真实图片分析
及外部灵感抓取均显式关闭，供应商审核和正式发布运维验收仍未完成。
处理方法、测试证据、完成度和陈述边界见 [v0.2问题文档](v0.2问题文档.md)。
本次未调用真实 Provider，因此不更新历史 Citation Correctness 指标，不宣称 P0 发布门禁已经清零。

修复顺序固定为：`FIX-01～03 → FIX-04～05 → FIX-06～09 → FIX-10`。每组修复完成后必须重跑
相关测试并停止汇报；P0 未清零前不启动面向外部用户的新功能。

## 二、新功能的需求分析

v0.2 的目标不是增加更多 Agent，而是把 v0.1 的“理解并记录”升级为一个可持续的个人健康行动
闭环：`随手记录 → 状态理解 → 用户确认 → 小行动 → 7 天反馈 → 复盘调整`。

| 编号 | 优先级 | 用户问题 | 功能需求 | 核心验收 |
|---|---|---|---|---|
| REQ-01 | Must | Agent 工作 20 秒以上时，用户不知道是否卡住，也无法安全离开页面 | 新增可观察 Agent Run：显示排队、理解、执行、待确认、校验、完成和失败状态；支持取消、后台继续、断线重连与 App 重启恢复 | 状态与服务端一致；恢复不重复写入；长任务可取消；所有状态有客户端和集成测试 |
| REQ-02 | Must | 系统不会稳定记住用户偏好，用户也不知道 AI 记住了什么 | 新增 Memory Center：展示用户声明、偏好、限制和待确认推断；允许纠正、删除、全部清空、暂停记忆和导出 | 所有持久记忆可解释、可操作；跨账号串读为 0；删除后 Prompt、缓存和导出均不可见 |
| REQ-03 | Must | 当前建议通常是一次性的，缺少执行过程和结果复盘 | 新增 7 天微实验：系统基于目标和近期记录提出一个低风险小行动，用户确认后启动，每日轻量反馈，期末复盘继续、调整或结束 | 创建、暂停、退出、反馈和复盘 E2E 通过；缺数据不判定失败；不得生成医疗或虚假因果结论 |
| REQ-04 | Should | 普通界面需要简洁，但项目展示和排障又需要解释 Agent 如何工作 | 新增 Journey X-Ray：仅在 Development/受控 Preview 中显示计划、工具、Observation、重规划、引用、延迟和成本；普通用户只看到自然语言依据 | Production 不包含 X-Ray 入口；受控模式可用同一 trace 还原一次完整 Run |
| REQ-05 | Should | 用户看到引用，但无法快速判断来源是否可靠、何时更新 | 新增 Evidence View：展示来源名称、适用地区、版本、更新时间、相关片段和“为何引用”；支持无依据时明确拒答 | 每个健康事实 claim 可定位到有效来源；过期或撤回来源不能继续生成答案 |
| REQ-06 | Should | 当前交付依赖现场环境，真实模型偶发延迟会影响演示稳定性 | 新增三种明确标识的交付模式：Local Mock、脱敏 Replay、授权 Live；Replay 使用版本化 Run Event，不伪装成实时模型 | 三种模式视觉标签清晰；新环境 15 分钟内可启动 Local；Replay 可离线稳定复现核心场景 |
| REQ-07 | Could | Journey 页只有数据总结，缺少真正有价值的长期变化解释 | 新增自适应 Journey：按 7/30 天展示事实、数据完整度、相关性观察和下一步选择，复盘结论经用户确认后才能进入记忆 | 事实与推断视觉分层；无数据不生成趋势；用户能拒绝建议且不影响记录功能 |

功能依赖顺序为：先完成 P0 修复和基线重建，再开发 `REQ-01`；随后完成 `REQ-02`，以它作为
`REQ-03` 和 `REQ-07` 的上下文基础；`REQ-04～06` 在核心链路稳定后统一完成交付验收。

v0.2 明确不包含：增加自治 Agent 数量、Agent 群聊、食物图片正式发布、语音、视频、自由网页
搜索、通用浏览器 Agent、HealthKit/Health Connect、医疗诊断，以及未经单独授权的公网部署、
商店签名、提交或推送。
