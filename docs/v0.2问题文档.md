## FIX-01：实验与内部能力可能泄漏到正式环境

**遇到了什么问题**

- 图片入口在客户端变量缺失时默认开启，不符合 fail-closed 原则。
- 登录页把本地演示账号和密码写死在客户端源码中，并无条件展示快捷登录入口。
- 普通用户结果页直接展示 Agent 工具、Provider、模型、Trace、延迟和费用。
- Production 后端允许 `AGENT_PROVIDER=mock`，可能让模拟结果进入正式环境。

**使用了什么技术解决**

- 在 Expo `app.config.js` 中建立按构建变体生成的 runtime capability manifest；图片、测试账号和
  Agent 调试详情只有 Development 且显式开启时才为 `true`。
- 客户端通过 `expo-constants` 读取已签入构建 manifest 的能力，不再根据变量缺失做乐观判断；
  manifest 缺失、字段缺失和非 Development 变体统一返回关闭。
- 本地测试账号改为由 Development 构建阶段从 `.env` 注入，移除业务源码中的固定凭据；
  Preview/Production manifest 中账号值固定为 `null`。
- 普通用户界面隐藏工具、Provider、Trace 和费用，只保留结果、确认操作及通用降级提示。
- FastAPI Settings 增加 staging/production fail-fast 校验：测试账号或 `AGENT_PROVIDER=mock` 均拒绝
  启动；Staging/Production Compose 关闭种子账号并要求显式指定已批准的非 Mock Provider。
- 使用 Jest 覆盖 manifest 缺失、Development 显式开启、Production 强制关闭、登录入口和首页
  调试详情；使用 Node 脚本验证 Development/Preview/Production 三种构建变体。

## FIX-02：知识回答可能没有有效引用

**遇到了什么问题**

- `run_knowledge` 只处理“模型返回了 citation id，但 id 全部非法”的情况。
- 当模型返回非空答案但 `cited_chunk_ids=[]` 时，系统可能把没有依据的健康知识回答直接交给用户。
- 原链路没有明确记录 Citation Verifier 是否触发确定性回退或最终拒答。

**使用了什么技术解决**

- 在最终响应门增加服务端 Citation Verifier，把模型引用限制在本次检索得到的 chunk allowlist 内。
- 空引用、非法引用或无法构造合法 Citation 时不信任模型答案：优先使用受控知识片段生成确定性
  fallback，并附上真实 chunk id。
- 如果检索片段本身也无法形成合法引用，则返回 `insufficient_context`，记录
  `citation_verification_failed`，不编造引用。
- Trace 增加 `citation_count`、`citation_fallback_used` 和 `citation_verification`，区分合法通过、
  安全回退与校验失败。
- 使用 Pytest 参数化覆盖空引用、非法引用、合法引用及防御性拒答四类路径。

**完成度：100%（工程漏洞修复），真实质量指标待复验**

- 空引用和非法引用均被转换为带有效来源的确定性结果；合法引用保持原模型答案；无法建立引用时
  明确拒答。
- PostgreSQL Docker 测试环境中 Settings 与 Agent Unit 合计 30 条测试通过；Citation Gate 的空引用、
  非法引用、合法引用和最终拒答路径均包含在内。
- Docker 全量 107 条后端/评测测试通过，Mock `citation_support_rate=0.9583`，达到 0.95 门槛。
- 本次不调用真实 Provider：FIX-03 发布验收尚未完成，且不能用 Mock 结果覆盖历史真实 Citation
  Correctness 0.9083。后续真实门禁完成后再把新指标写入本文。

## FIX-03：外部模型缺少明确授权与可验证的数据生命周期

**遇到了什么问题**

- 文字 Agent 只检查服务端 Provider 配置，未验证当前账号是否同意；续跑和底层模型重试也缺少独立门禁。
- 模型上下文可能携带完整个人资料、逐条记录或线程标识，缺少统一的出站字段白名单。
- Provider 异常、第三方 SDK 日志及运维 Trace 可能保留输入内容或凭据。
- Agent Run、工具 Trace、候选令牌、检查点、线程记忆和确认回放缓存缺少统一保留与删除路径；
  简单删除还可能与正在执行的请求竞争，导致删除后重新写入。
- 实验图片接口使用独立 Provider，不能把文字授权视为图片上传授权。
- 仓库没有供应商侧删除、备份到期清理和删除后恢复演练的证明，不能承诺“所有副本已彻底删除”。

**使用了什么技术解决**

- 服务端增加 `agent_consents` 和按账号、政策版本绑定的明确授权。政策指纹覆盖供应商、
  Endpoint、模型、发送范围及保留/删除说明；变更后旧授权失效。首次调用、续跑、每次重试都在
  构建真实 SDK 或发送请求之前校验，拒绝时返回 `consent_required` / `consent_outdated`。
- 增加默认关闭的 `AGENT_EXTERNAL_ENABLED`。开启前必须配置无凭据的 HTTPS 政策地址及明确的
  供应商保留/删除说明；配置校验不等于政策已审核，运营证据仍需人工验收。真实图片 API 单独
  返回 `food_image_external_disabled`，保留本地 Mock 图片演示，不复用文字授权。
- 对每种模型任务建立 Prompt 白名单：仅保留本次所需文字、目标和记录聚合、最多 8 次任务状态
  摘要、最多 5 个公开知识片段；排除账号资料、生日、用户/Run ID 及逐条历史记录。过滤已知账号
  标识、常见联系方式与凭据。自由文字仍可能含健康信息，授权页明确告知，不能宣称通用 PII 识别率 100%。
- 对入库及读取的运维 Trace 隐去自由文本，对工具摘要使用字段白名单；异常使用固定错误码，
  不记录原始异常体。关闭本链路的 LangSmith/LiteLLM 内容遥测，保护 Journey/Uvicorn 日志，
  访问日志不记录客户端 IP 和查询参数。历史导出日志不由此代码自动清除。
- 新增以下已鉴权接口，同时更新 OpenAPI 快照与 TypeScript 契约：

  | 接口 | 作用 |
  |---|---|
  | `GET /api/v1/agent/privacy` | 获取当前供应商、授权版本、发送与保留说明 |
  | `PUT /api/v1/agent/privacy/consent` | 主动授权或撤回；不能代其他账号授权 |
  | `DELETE /api/v1/agent/privacy/data` | 撤回授权并删除当前账号活跃数据库中的 Agent 数据 |

- 运行、续跑、确认、Mock 图片分析、撤回和删除使用同一 PostgreSQL 用户行锁，删除等待已有请求
  完成后再清理，避免旧请求重新入库；这不是即时取消正在执行的 Provider 请求。
- 删除清理 Run/工具/候选令牌/检查点/线程记忆/Agent 确认回放缓存，不删除其他账号或已经确认的
  健康记录。当天已消费金额转为不含用户、Run 或模型标识的日汇总，避免删历史后重置费用预算。
  返回值固定 `provider_data_deleted=false`，不伪造供应商删除证明。
- 默认保留 7 天，可配置 1～30 天；服务启动及每小时执行清理，访问 Agent 数据时也检查过期。
  健康运行时后台清理存在最多约一小时调度延迟，停机期间不保证按时执行；可运行
  `python -m app.purge_agent_data` 手动触发。
- 客户端“我的 → 外部 AI 与数据”显示服务端政策，默认不勾选；主动授权需选择并点击确认，
  政策变更清空旧选择，撤回/删除二次确认。离线不提交；网络失败不假报成功。首页未授权时先
  拦截文字发送；删除成功后清空 Agent 界面/内存缓存，并以版本标记丢弃迟到响应，保留手动记录和离线队列。
- 2026-08-31 补充部署审核门禁：新增 `AGENT_PROVIDER_REVIEW_JSON`，必须由实际部署负责人提供
  `approved` 状态、当前披露指纹、审核人、审核时间/有效期以及保留、删除、恢复证据引用；有效期
  不超过 90 天。缺失、过期、配置不匹配时，即使已有用户同意且外部开关为 true，也拒绝真实调用。
  这是有责任人的审核声明，不是自动法律审查或供应商签名；示例文件始终为 `pending`。
- 新增 `python -m app.check_agent_privacy_release` 只读检查，输出当前披露指纹和门禁状态，
  不输出密钥、用户数据，不替负责人批准。审核记录变化也会令旧用户授权失效。
- 新增 `infra/privacy/backup.mjs`：校验明确的 Journey Compose 容器归属，使用 AES-256-GCM
  认证加密，备份元数据和有效期一起防篡改；目录 0700、文件/独立密钥 0600。默认排除 Agent
  运行、工具、候选、线程、授权、会话和幂等缓存的表数据；迁移回滚备份需显式选择保留这些数据。
  `.dockerignore` 同时排除 `artifacts/`、`reports/`，备份和密钥不会进入新 Docker 构建上下文。
- 备份有效期 1～7 天，过期归档拒绝恢复；`prune` 默认仅列清单，显式确认后只删除校验通过的
  过期受管归档，不扫描删除密钥、旧 `.dump` 或任意目录。当前工具限定小型数据库，归档上限 64 MiB。
  未安装系统级定时任务；公开部署必须落实定时清理和密钥托管，不能把“到期不可恢复”说成“磁盘文件已删除”。
- 恢复采用“所有旧 Agent 状态统一丢弃”，而不是恢复可能同样过期的删除登记表：新建无网络、
  无端口的临时 PostgreSQL，事务化恢复、清理 Run/候选/线程/授权/Agent 回放，并撤销旧会话，
  比较用户资料与已确认健康记录的数量和内容摘要，验证成功才出具报告，最后销毁临时库。
  工具不覆盖、不开放、不自动切换任何业务数据库。原 `infra/staging/restore.sh` 的原地
  `pg_restore --clean` 旁路已关闭，改为仅运行隔离演练。
